RED-024 - a note source outlived its manifest line
==================================================================================================

SUBJECT: ~/orchestra/notes_gen.py       (outside the repository, by design - D-17)
         web/notes/emit.mjs             loadNotes()
         tests/test_notes_freshness.py

taken 2026-08-24 during T-C7, on this host, python 3.10.12, node v20.20.2

THE DEFECT. A method note is TWO artefacts that pin each other: the prose at
web/notes/src/<slug>.md and one line of web/notes/manifest.json. The generator wrote the prose
inside build() and the manifest once, at the end of main(), after every topic had been drafted.
Those are not two adjacent statements - between them sit all the model calls of every remaining
note, fourteen minutes on the run of 2026-08-20 14:21. A process that dies anywhere in that span
leaves a source no manifest line covers, and loadNotes() throws on exactly that pair. The build
then fails on the MOMENT THE PROCESS DIED rather than on anything about the note.

RUN 1 IS AGAINST THE PRE-REPAIR GENERATOR, NOT A DESCRIPTION OF IT. The bytes come from
~/orchestra's git history at 765eb82, replayed with --generator, so this artefact could be re-taken
after the repair had landed instead of becoming a paragraph asserting what the old code used to do.
RUN 2, below it, is the same tool over the repaired generator.

WHAT IS SIMULATED, AND HOW. A two-topic capture is replayed from prose this repository already
holds - no model is called, but measure(), measure_links(), check_addresses() and the whole
assembly path run for real. Every mutation under web/notes/ is recorded, and the tree each one
leaves is judged by both readers of the pair. Each judged tree is, byte for byte, what a kill at
that instant leaves. A real SIGKILL then confirms one of them, and a third phase forces the capture
to measure red to check that a REFUSED capture strands nothing either.

TWO TOPICS AND NOT ONE, BECAUSE THE ONE-NOTE RUN UNDERSTATES THIS. With a single topic the window
is the tail of one build(); with two it is visibly the whole of the second note's drafting, and the
first note's source sits unpinned across all of it.

THE GATE COLUMN NAMES THREE STATES, NOT TWO, AND THE FIRST DRAFT OF THIS TOOL NAMED TWO. It
reported pytest's summary line and treated anything without the word "failed" as clean - so a
module that had DISARMED ITSELF and judged nothing was counted as a gate that looked and found
nothing wrong. That is a refusal returned as a zero, inside the artefact whose subject is refusals
returned as zeroes. Fable found it. Outcomes are now read per test: passed is a gate that ran and
held, failed is a gate that ran and refused, and "did not run" is check_did_not_run and is neither.
The same correction applies to the manifest column: a torn manifest reads UNREADABLE, never as a
manifest pinning nothing.

RUN 2 - THE SAME KILL POINTS, AFTER THE T-C7 REPAIR
==================================================================================================

WHAT CHANGED IN THE GENERATOR. build() no longer writes web/notes/src/<slug>.md. It stages the
prose at .<slug>.md.staged - a name in neither reader's filter, since loadNotes() takes
readdirSync(SRC).filter(f => f.endsWith(".md")) and notes_support.sources() takes SRC.glob("*.md").
publish() then makes the pair visible per note, inside the loop, in two atomic renames: THE
MANIFEST LINE FIRST, the prose second. Both files are written to a temporary path and moved with
os.replace, so no reader-visible path is ever mutated by a primitive that can be interrupted
half-way - which also removed the torn-JSON state run 1 found at mutation 3, a third broken tree
the task had not named.

WHY THAT ORDER. Two files cannot be published in one filesystem operation, so one is visible first
and the only question is which intermediate state a kill can leave. Prose first leaves a source
with no line to pin it, and loadNotes() throws on that - the defect above. The line first leaves an
entry for a note that is not there yet, which loadNotes() never looks at: it enumerates the source
directory and reads the manifest by slug, so an entry nobody asks for costs nothing.

WHAT CHANGED IN THE REPOSITORY, AND WHY IT MAKES THIS RUN LOOK WORSE THAN IT OTHERWISE WOULD.
tests/test_notes_freshness.py stood its whole module down whenever web/notes/src/ was empty - which
is exactly the tree the repaired order produces for the FIRST note, so the one gate that refuses a
pin with no note behind it was disarmed by the same emptiness that produced the state it judges.
The skip condition now requires both halves of the pair to be absent. The consequence is honest
rather than flattering: this run reports TWO refused kill points where an earlier draft of the
report claimed one, because the second had never been judged at all. Fable found that too.

THE RESIDUAL IS PRINTED RATHER THAN LEFT OUT. The freshness gate pins the pair in BOTH directions,
so the intermediate state that is green for the build is red for that gate. No ordering satisfies a
gate that refuses both directions of a mismatch; the only thing that would is making the pair one
file, which is a change to a committed artefact and to LAW-NOTES-FRESHNESS and therefore a judge's
call. What the repair achieves is measurable and is the whole of what it claims: the window fell
from every remaining model call of the run to the gap between two adjacent os.replace calls with no
work between them, and the build is green at every instant of it.
