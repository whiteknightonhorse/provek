THE PATCHES ARE PROVEN, NOT ASSERTED
------------------------------------
A saved patch that cannot be replayed is not insurance, and "I saved it" is exactly the class of
claim this project exists to catch. Each patch was applied to its recorded base in a scratch index
and the resulting tree hash compared to the stash's own tree:

  T-G2-stash-a2-5-parked-work.patch            -> 3fb66b65b6aba951ad96d43f34b204fe5c73b333  MATCH
  T-G2-stash-a2-5-parked-work.staged-only.patch -> 961d53879da5cca69cb079d84e03f0add069fb2d  MATCH
  T-G2-stash-wip-0b7b3d9.patch                 -> b8b6dd70d952a4962e285aa2c4bde500cef1bc70  MATCH

The first and third hashes are `git rev-parse <stash>^{tree}` for the two dropped stashes. The
recovery command is therefore exact:
  git read-tree <base> && git apply --cached <patch> && git write-tree

Both stashes carried a staged/unstaged split. `git stash show -p` shows only the combined diff, so
a single patch would have silently flattened the split and lost which three files were staged. For
4ee36b20 the staged half was exactly evidence/RED-019-*.txt, evidence/RED-019-generator.py and
tests/test_apply_names_the_probe_cost.py; the other seven files were unstaged. Both halves are
saved, which is why there are three patches for two stashes.

WHAT THIS TASK FOUND THAT THE RULING DID NOT KNOW
-------------------------------------------------
1. THE INDICES HAD DRIFTED, AND THE RULING IS WRITTEN IN INDICES.
   The ruling names stash@{0} (T-A2-5) and stash@{1} (WIP 0b7b3d9). By the time it was executed a
   THIRD stash had been pushed on top — "T-H4 parked by T-C6", stash commit e64678f337de..., landed
   05:09 on 2026-08-24 — and the stack had become:
       stash@{0}  e64678f  T-H4 parked work        <- NOT in the ruling
       stash@{1}  4ee36b2  T-A2-5 parked work      <- ruling's stash@{0}
       stash@{2}  891b126  WIP 0b7b3d9             <- ruling's stash@{1}
   `git stash drop stash@{0}` twice, which is what the ruling says literally, would have destroyed
   T-H4's parked work and left the trap in place — the exact inversion of the ruling's intent.
   A stash reference is a POSITION IN A STACK, not a name for a piece of work, and a ruling that
   pins work by index has a shelf life of one push. Both drops here were done by verifying
   index -> SHA immediately before each drop, and the SHAs are recorded above.

2. `git stash list` IS NOT EMPTY, AND EMPTYING IT WOULD HAVE BEEN THE DEFECT.
   The acceptance criterion "git stash list is empty" was written when both stashes were all the
   stashes. e64678f is live parked work belonging to T-H4/T-C6: docs/INTAKE_OPERATIONS.md rewritten
   by a run that died on API 529 and never committed. It has not reached main. It is not this
   task's to delete, and satisfying the criterion literally would have thrown away in-flight work
   to make a list look tidy. The criterion is reported unmet, with the reason, rather than met by
   damage. e64678f is intact and untouched.

3. evidence/ IS EXEMPT FROM THE LANGUAGE RATCHET, WHICH MAKES "SAVE THE PATCH VERBATIM" SHARP.
   891b1263 carries an untracked tree whose largest members are the operator's Russian working
   documents and a 146 KB private specification. scripts/ratchet_language.py exempts evidence/ by
   name ("archived evidence: historical run output is never rewritten"), so a verbatim dump of
   that tree into evidence/ would have carried Russian operator documents onto the English-only
   public surface PAST the only gate that inspects for them, permanently, pinned by head_sha.
   The tracked half is saved as a replayable patch; the untracked half is saved as an inventory of
   path, blob SHA and byte size. The blob SHA is the verbatim identity of each file, so the record
   is exact and verifiable without reproducing content that does not belong in this repository.
   Paths are recorded in git's own octal-escaped form, which is pure ASCII.

WHY THE STASHES ARE GONE RATHER THAN KEPT
-----------------------------------------
A stash is the one place in this repository where work is invisible to every gate. It is not
covered by the ratchets, it is not in the history the passports pin, and `git stash list` is read
by nobody — which is how 4ee36b20 sat carrying a refuted number for long enough to mislead a task
formulation. The patches in evidence/ are the opposite: tracked, pushed, judged by the same gates
as everything else, and readable by the next agent WITHOUT the one operation that made the stash
dangerous — being applied over HEAD by accident.
