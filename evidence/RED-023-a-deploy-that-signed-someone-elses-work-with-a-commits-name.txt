=== 7. THE PERMISSION STATES, MEASURED - AND THE PREDICTION CAME OUT BACKWARDS ===

Fable's second refusal said the clean path's re-reading of every tracked file was defended by no
test that could fail, and that the state it CLAIMED to cover ("a tracked file under a directory
this process cannot enter") probably never reached that path at all - git would report the file as
deleted and the tree would be refused as dirty instead. Both halves were built as fixtures. The
prediction was inverted, and the module's comment had to be rewritten around the measurement:

  (a) tracked file that cannot be READ, in a directory that CAN be entered
      $ chmod 000 plain.txt
      porcelain      -> ['plain.txt']        git cannot compare it to the index, so: MODIFIED
      content_digest -> None
      decide         -> 3                    DIRTY_REFUSED, before the digest is ever consulted

      Honest - the tree cannot be shown equal to HEAD - and misleading, because it names the path
      as uncommitted work and sends the operator to `git status`, which will say the same thing,
      rather than to the permission bit. Pinned by a test so the next person to improve it knows
      the behaviour was measured and not accidental.

  (b) tracked file under a directory that cannot be ENTERED
      $ chmod 000 d/
      porcelain      -> []                   git warns, exits 0, and omits the subtree: CLEAN
      content_digest -> None
      decide         -> 4                    UNREADABLE

      This is the case the clean path's reading exists for, and it is the one Fable expected not to
      reach it. Without that reading the tree above is labelled with a commit's short sha, clean,
      confidently, over content nothing opened.

Both cases are now tests, skipped only under euid 0 - where `chmod 000` means nothing and the
fixture could not express its own subject. Neither this host nor the CI runner is root.

=== THE FINDING RUN 4 TURNED UP, WHICH IS NOT FIXED IN THIS COMMIT ===

A directory git cannot read is reported by `publishable_tree._porcelain` as no dirty paths at all,
so BOTH gates built on it call such a tree clean. Measured end to end, with an uncommitted file
inside a `chmod 000` directory:

    porcelain -> []
    classify  -> 0        (PUBLISHABLE=0 FOREIGN=3 UNREADABLE=4)
    decide    -> 0  202ae11  commit_dirty=false

The scheduler would publish it and this module would sign it with a commit's short sha. The hole is
in a module belonging to T-C5 and shared with the scheduler's gate, so it is written into
`~/orchestra/FINDINGS.md` for the judge rather than repaired in passing by a neighbouring task.

HALF OF IT IS CLOSED HERE ANYWAY, and only half - see run 7. This module's clean path re-reads every
file `git ls-files` names, which catches the TRACKED case (b) without touching T-C5's module. The
UNTRACKED file in the reading above stays invisible, because `ls-files` omits it exactly as `status`
does, and the scheduler's gate has no equivalent second reading at all. So the claim this module
makes is: it refuses every dirty path git REPORTS, it refuses a tree holding a tracked file it
cannot read, and it does not claim git reported everything.
