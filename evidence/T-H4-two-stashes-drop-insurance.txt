============================================================================================
Recorded 2026-08-24. This file is the insurance behind two `git stash drop` calls, and the index of
the patch beside it. It follows the precedent set by `evidence/T-G2-*`: a saved patch that cannot be
replayed is not insurance, and "I saved it" is exactly the class of claim this project exists to
catch.

READ THE TENSE BEFORE READING THE FILE
--------------------------------------
This file is committed BEFORE the push and BEFORE either drop, in the same commit as the work it
describes, because that is the only moment it can be written truthfully: history is not rewritten in
this repository (passports pin `head_sha`), so a sentence committed here cannot be corrected
afterwards, only contradicted.

An earlier draft of this file — the one carried inside the stash it describes — did not respect that.
It said the stash's file "was applied to a clean HEAD, corrected, and committed to `main` in the same
task that dropped it", in the past tense, while sitting untracked in a working tree where none of
those three things had happened. Had it been committed unchanged it would have become a false claim
in stone, in `evidence/`, which is this project's founding defect (a claim stronger than its
artefact) committed inside the corpus kept to detect it.

That draft was also NAMED for the claim: `T-H4-stash-e64678f-landed-then-dropped.txt`. A name travels
without its content — through `git log --stat`, through directory listings, through links from other
files — so a reader of the stat line would have received "landed-then-dropped" without ever reaching
the paragraph qualifying it, and "dropped" is the half that is unverifiable from a clone FOREVER (see
below). The name also pinned the one stash that did not, in the end, carry the work. It is renamed
here for the same reason its sentences are rewritten, and this is the only moment either was legal.

The draft survives outside this repository, so the quotation above is checkable rather than asserted:

WHY THE DROPS ARE SAFE, AND WHICH HALF OF THAT A READER CAN CHECK
------------------------------------------------------------------
Two different things are offered here and they are not equally strong, so they are labelled.

  INSURANCE (reproducible forever, by anyone with a clone). The patch replays onto a369de3 — a commit
  in this repository's history — and yields tree 03bfeccf5ab9af38766e030d6166fd6ea0e37b4e. That is
  the transcript above, it needs nothing but this repository, and it survives both drops. The
  document text it reconstructs is therefore recoverable whatever happens to the stashes.

  TESTIMONY (a reading, not a check). Everything that identifies those bytes with the STASHES is a
  measurement this task took and no one can retake, because stash objects never leave this host:
  that 03bfecc was e64678f's tree; the tree, index and third-parent hashes of both stashes; and the
  `git diff --stat` above, whose right-hand operand `fc3170a` exists only inside f6b949e. (Its
  left-hand operand `5af7389` is not testimony — the patch header `index c1431a0..5af7389` puts that
  blob id in the clone.) After the drops nothing can confirm that the stashes held nothing beyond
  what is written here. This file says so rather than letting the hash list imply otherwise.

What makes the drops correct is that the work stops being parked HERE: the commit carrying this file
also carries the stashed content — `docs/INTAKE_OPERATIONS.md` and the `tasks/lessons.md` bracket —
applied from f6b949e onto a clean HEAD and then corrected as recorded below. A reader checks the
presence of that work with `git show --stat` on the commit this file arrived in, without trusting any
sentence here.

Neither dropped stash is a byte-for-byte duplicate of what is committed, and calling them duplicates
would be exactly the overstatement this file was rewritten to remove. e64678f carries the document
stamped 04:37 where the commit carries a later reading; f6b949e carries the superseded draft of this
file under its old name. Both are RECOVERABLE FROM this commit up to those named differences, which
is the honest form of the claim and the reason the drops lose nothing.

What a reader can never verify from the repository is that the drops happened at all, because a
dropped stash leaves no trace in a clone — stash refs are local to the host. The drops are performed
by this task after `./scripts/push.sh` returns, each one preceded by resolving the index to a SHA and
comparing it against the SHA recorded above, because a stash reference is a POSITION IN A STACK and
not a name for a piece of work (the lesson T-G2 paid for: `stash@{0}` means a different commit after
every drop). The evidence for the drops is `git stash list` being empty on this host, and this file
is not that evidence.

THE LABEL MOVED AND THE CODES DID NOT, WHICH IS WORTH MORE THAN EITHER READING ALONE
-------------------------------------------------------------------------------------
The four codes are identical across all three readings while the deployment label changed from
`a369de3` to `57a267c`. Measured, that means the 405 is a fact about two deployment labels rather
than one, so it is not an artefact of a single upload.

The comparison is deliberately footed on **04:37** rather than on 07:04, even though 07:04 is the
more recent of the two earlier readings. 04:37's table and its `a369de3` label line are inside the
patch this commit carries, so that half of the comparison stays checkable after both drops; 07:04
lived only in a stash blob this task destroys, and resting the argument on it would have made a
published inference depend on a reading no reader can reach.

It does NOT by itself establish that the handler belongs to the published tree. That step needs a
premise this task did not measure: that a Pages deployment serves only what it carries, rather than
inheriting a working Function from its predecessor. The premise is ordinary platform behaviour and it
is stated rather than assumed silently, because "survives a redeploy therefore belongs to the tree"
is one inference longer than the reading. Who deployed `57a267c`, and from which tree, is also not
measured here.

The four line references the document makes into `web/functions/api/apply.js` were checked against
the tree being committed, because a line number is a claim: `:196` is the 405 return inside
`onRequestGet`, `:91` is the `if (!env.INTAKE)` 503 guard, and `:38`–`:80` bound the validation that
refuses an invalid submission before the first `put`. All four resolve as written in a 197-line file.
