RED-005 - the badge test proved able to fail, 2026-08-20

A test that cannot fail is a declaration (CLAUDE.md invariant 5). Four defects were injected into
README.md, one per guard, and the file was restored afterwards from a copy taken before the
injection - the suite is green again in the same session.

The defects are the four ways a badge lies, and each was chosen because it is what a hurried commit
actually does, not what a malicious one would:

  1. `![build](https://img.shields.io/badge/build-passing-brightgreen)`
     The decorative badge. Renders in the project's own green, is wrapped in no link, and takes its
     text from its own URL. This is the exact claim-stronger-than-artefact defect the project is
     built to detect, which is why its presence in this repository's own README would be the worst
     available failure. Caught twice, by the no-link guard and by the endpoint ban.

  2. the `codeql` badge repointed at `nightly-fuzz.yml`, a workflow this repository does not have
     A badge for a workflow that never existed - or that was deleted after the badge was pasted -
     keeps rendering the last colour it ever had. Nothing about the image says the run is gone.

  3. the OpenSSF badge relinked from our report to `https://scorecard.dev/`
     The badge still shows our real score; the link now lands on the service's front page. A reader
     who clicks to check the number arrives somewhere it cannot be checked, which is worse than no
     link because it looks like it was followed.

  4. `## What the badges assert` renamed to `## Security`
     Three green ticks and no statement of what they cover. A green `codeql` badge means the
     analysis COMPLETED, not that it found nothing, and an unexplained tick is read as covering
     everything.
